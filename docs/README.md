## 核心结论

1. 家政服务预约是本地生活 O2O 的垂直领域，不能做成泛商城。
2. 标准单次服务、周期服务、长期住家服务和咨询撮合服务的履约方式不同，不应在一个 MVP 中全部做深。
3. 平台的核心对象不是“商品”，而是“服务项目 + 服务人员 + 可用时段 + 上门地址 + 履约记录”。
4. 时段占用、重复下单、重复支付、取消退款和改派是后端必须处理的一致性场景。
5. 身份核验、健康证明、技能证书、服务记录和售后证据是家政平台区别于普通商城的关键能力。
6. 毕设首版建议聚焦“标准化上门家政服务预约”，以保洁、家电清洗、整理收纳等单次或周期服务为主。
7. 后端采用模块化单体，不引入微服务，首版只依赖 Spring Boot 和 MySQL 即可完成核心闭环。
8. 企业级增强版通过 Redis、RocketMQ、MinIO、高德地图和 WebSocket 增加在线人员、异步事件、抢单、文件存储和实时通知，但仍保持单体应用。
9. 代码脚手架应按 `05-脚手架搭建说明书.md` 实施，先完成可运行基础设施和模块边界，再进入业务开发。
10. 当前实际执行顺序以 `06-第一阶段最小骨架集成.md` 为准：先完成纯技术骨架，暂不创建业务模块。
11. 业务设计最终采用单公司自营模式：统一品牌、全职和兼职人员供给、公司统一派单与售后，不做商家入驻、个人开店和平台抽佣。
