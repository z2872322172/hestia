## 2. 技术选型与取舍

### 2.1 为什么用 Navigation 而不是 router

`@ohos.router` 在 API 12 起已标记废弃。选 `Navigation` 的三个实际理由：

1. **参数类型安全**：`router.pushUrl({ url, params })` 的 `params` 是 `Object`，取出来必须强转，ArkTS 严格模式下很容易在编译期或运行期炸。`NavPathStack` 可以配合显式 `interface` 声明参数。
2. **返回栈可控**：登录成功后要**清空**欢迎页和登录页，`router` 只能 `replaceUrl` 一次一个，`NavPathStack.clear()` 一行搞定。
3. **转场动画与手势返回**：`NavDestination` 自带侧滑返回，作业演示时手感明显更好。

> 如果教材强制要求 `router`，见附录 A 的降级写法。

### 2.2 零第三方依赖

不引任何三方网络库、UI 库。理由：

- 鸿蒙三方库生态在 API 12 上版本参差，作业环境拉依赖失败会直接卡死进度；
- 网络请求用系统 `@ohos.net.http` 足够；
- UI 全部手写，答辩时"每个像素都是自己写的"反而是加分项。

### 2.3 零图片资源

设计稿里的图标全是 SVG 线性图标。**不导出 PNG**，直接用 `Path` 组件按原 path 坐标绘制。

好处：工程里没有一张图片，`resources/base/media` 只需放应用图标，编译不会因为缺资源失败。

```ts
// 24×24 坐标系直接搬设计稿的 path，Path 的 commands 坐标单位就是 vp
Path()
  .commands('M3 10 L12 3 L21 10 L21 19 A2 2 0 0 1 19 21 L5 21 A2 2 0 0 1 3 19 Z')
  .fill(Color.Transparent)
  .stroke('#C2592C')
  .strokeWidth(1.5)
  .width(24)
  .height(24)
```

> **注意**：`Path` 的 `commands` 不做 viewBox 缩放，坐标就是 vp。设计稿的 SVG 是 `viewBox="0 0 24 24"`，所以 `width/height` 统一给 24（或把坐标整体乘系数）。**不要**写 `.width(22)` 又用 24 的坐标，会裁掉一部分。

import { RouteName, ServiceListParam, ServiceDetailParam, /* ... */ } from '../common/RouteName';

@Entry
@Component
struct Index {
  // @Provide 让所有后代页面都能拿到栈，不用层层传参
  @Provide('pageStack') pageStack: NavPathStack = new NavPathStack();

  @Builder
  routeMap(name: string, param: object) {
    if (name === RouteName.MAIN) {
      MainPage();
    } else if (name === RouteName.LOGIN) {
      LoginPage();
    } else if (name === RouteName.SERVICE_LIST) {
      ServiceListPage({ param: param as ServiceListParam });
    } else if (name === RouteName.SERVICE_DETAIL) {
      ServiceDetailPage({ param: param as ServiceDetailParam });
    } else if (name === RouteName.BOOKING) {
      BookingPage({ param: param as BookingParam });
    } else if (name === RouteName.PAYMENT) {
      PaymentPage({ param: param as PaymentParam });
    } else if (name === RouteName.ORDER_DETAIL) {
      OrderDetailPage({ param: param as OrderDetailParam });
    } else if (name === RouteName.REVIEW) {
      ReviewPage({ param: param as ReviewParam });
    } else if (name === RouteName.ADDRESS) {
      AddressPage({ param: param as AddressParam });
    }
  }

  build() {
    Navigation(this.pageStack) {
      WelcomePage();
    }
    .hideTitleBar(true)
    .mode(NavigationMode.Stack)
    .navDestination(this.routeMap);
  }
}

### 6.2 ApiClient

职责：拼 URL、加 token、解析 `Result`、统一抛错、401 清 token、失败降级 Mock。

```ts
// api/ApiClient.ets
import http from '@ohos.net.http';
import { ApiResult } from '../model/ApiTypes';
import { Storage } from '../common/Storage';

export class ApiError extends Error {
  code: string;
  traceId: string;

  constructor(code: string, message: string, traceId: string) {
    super(message);
    this.code = code;
    this.traceId = traceId;
  }
}

export class ApiClient {
  // 模拟器访问宿主机用 10.0.2.2；真机改成电脑局域网 IP，例如 http://192.168.1.8:8080/api/v1
  static readonly BASE_URL: string = 'http://10.0.2.2:8080/api/v1';

  static async request<T>(method: string, path: string, body?: object,
                          extraHeaders?: Record<string, string>): Promise<T> {
    const headers: Record<string, string> = {
      'Content-Type': 'application/json',
      'Accept': 'application/json'
    };

    const token: string = await Storage.getToken();
    if (token.length > 0) {
      headers['Authorization'] = 'Bearer ' + token;
    }
    if (extraHeaders) {
      Object.keys(extraHeaders).forEach((k: string) => {
        headers[k] = extraHeaders[k];
      });
    }

    const options: http.HttpRequestOptions = {
      method: method as http.RequestMethod,
      header: headers,
      connectTimeout: 8000,
      readTimeout: 8000,
      expectDataType: http.HttpDataType.STRING
    };
    if (body !== undefined) {
      options.extraData = JSON.stringify(body);
    }

    const request = http.createHttp();
    try {
      const resp = await request.request(ApiClient.BASE_URL + path, options);
      const raw: string = resp.result as string;

      // HTTP 401：令牌失效，清 token 后抛特定错误，由调用方跳登录
      if (resp.responseCode === 401) {
        await Storage.clearToken();
        throw new ApiError('AUTH_TOKEN_EXPIRED', '登录已过期，请重新登录', '');
      }

      const parsed: ApiResult<T> = JSON.parse(raw) as ApiResult<T>;
      if (parsed.code !== 'OK') {
        throw new ApiError(parsed.code, parsed.message, parsed.traceId);
      }
      return parsed.data;
    } finally {
      request.destroy();  // 必须销毁，否则连接泄漏
    }
  }

  static get<T>(path: string): Promise<T> {
    return ApiClient.request<T>('GET', path);
  }

  static post<T>(path: string, body?: object, headers?: Record<string, string>): Promise<T> {
    return ApiClient.request<T>('POST', path, body, headers);
  }

  static put<T>(path: string, body?: object): Promise<T> {
    return ApiClient.request<T>('PUT', path, body);
  }

  static delete<T>(path: string): Promise<T> {
    return ApiClient.request<T>('DELETE', path);
  }
}
```

**三个必须注意的点：**

1. `request.destroy()` 放在 `finally`，不销毁会泄漏连接，反复切页面后请求会挂。
2. `JSON.parse` 必须 `as` 强转，ArkTS 严格模式下 `JSON.parse` 返回 `Object`，不转型无法访问属性。
3. 后端 HTTP 状态码和业务码是**两套**：401 走 HTTP 状态码（`SecurityConfig` 的 `authenticationEntryPoint`），业务错误走 `code` 字段但 HTTP 可能仍是 200/4xx。所以先判 `responseCode === 401`，再判 `code !== 'OK'`。

### 6.3 Mock 降级策略

不是所有请求都降级——**写操作绝不降级**（否则会出现"UI 显示下单成功但后端没数据"的假象，答辩时最致命）。

| 场景 | 行为 |
| --- | --- |
| 读接口（分类/列表/详情/订单列表/消息/地址）网络异常 | 返回 `MockData` 对应数据，并在页面顶部显示"演示数据"角标 |
| 写接口（登录/下单/支付/评价/地址增删改）网络异常 | **不降级**，弹出"网络异常，请检查后端是否启动" |
| 业务错误（`code !== 'OK'`） | **不降级**，按错误码提示，因为这是后端明确拒绝 |

```ts
// 读接口降级示例
static async listCategories(): Promise<Category[]> {
  try {
    return await ApiClient.get<Category[]>('/public/service-categories');
  } catch (e) {
    if (e instanceof ApiError) {
      throw e;                    // 业务错误照常抛
    }
    MockData.markDegraded();      // 仅网络异常降级
    return MockData.categories();
  }
}
```

`MockData.markDegraded()` 写一个 `AppStorage` 标记，`HomeTab` 读到就显示角标。

### 6.4 Token 与本地存储

```ts
// common/Storage.ets
import preferences from '@ohos.data.preferences';
import common from '@ohos.app.ability.common';

const STORE_NAME: string = 'hestia_store';
const KEY_TOKEN: string = 'access_token';
const KEY_ACCOUNT: string = 'account_json';
const KEY_PHONE: string = 'remember_phone';

export class Storage {
  private static store: preferences.Preferences | null = null;

  static async init(context: common.UIAbilityContext): Promise<void> {
    Storage.store = await preferences.getPreferences(context, STORE_NAME);
  }

  static async getToken(): Promise<string> {
    if (Storage.store === null) return '';
    return await Storage.store.get(KEY_TOKEN, '') as string;
  }

  static async setToken(token: string): Promise<void> {
    if (Storage.store === null) return;
    await Storage.store.put(KEY_TOKEN, token);
    await Storage.store.flush();
  }

  static async clearToken(): Promise<void> {
    if (Storage.store === null) return;
    await Storage.store.delete(KEY_TOKEN);
    await Storage.store.flush();
  }
}
```

`Storage.init()` 在 `EntryAbility.onCreate` 里调用一次。**不要**在每个页面里 `getPreferences`，重复打开会报错。

### 8.2 前端聚合分组（订单 Tab）

后端 `GET /customer/bookings?status=` **只接受单个状态值**，但设计稿订单 Tab 有 5 个分组。这是本项目一个必须处理的错位：

| 前端 Tab | 后端 status 参数 | 说明 |
| --- | --- | --- |
| 全部 | 不传 | 直接分页 |
| 待支付 | `PENDING_PAYMENT` | 直接传 |
| 待服务 | `CONFIRMED` | **只传 CONFIRMED，EN_ROUTE 需另取** |
| 服务中 | `IN_SERVICE` | **PENDING_CONFIRM 需另取** |
| 已完成 | `COMPLETED` | 直接传 |

**实现方案**（推荐）：Tab 切换时按需发 1~2 个请求，前端合并去重后按 `createdAt` 倒序。

```ts
// 待服务 = CONFIRMED + EN_ROUTE
const [confirmed, enRoute] = await Promise.all([
  BookingApi.list('CONFIRMED', 1, 20),
  BookingApi.list('EN_ROUTE', 1, 20)
]);
const merged = confirmed.records.concat(enRoute.records)
  .sort((a, b) => b.createdAt.localeCompare(a.createdAt));
```

> 不建议"取全部再前端过滤"：分页会错乱（第 1 页过滤完可能只剩 2 条，用户以为没数据）。

**日期区间必须 ≤ 14 天**（后端约束），且 `dateFrom` 不得早于今天：

```ts
private buildDateRange(): string[] {
  const result: string[] = [];
  const today = new Date();
  for (let i = 0; i < 14; i++) {
    const d = new Date(today.getTime() + i * 86400000);
    result.push(this.formatDate(d));  // yyyy-MM-dd
  }
  return result;
}
```

**时段请求**：一次拉满 14 天，避免每切一天发一次请求。

```
GET /public/availability?serviceItemNo=SVC001&serviceAreaId=1&dateFrom=2026-10-24&dateTo=2026-11-06
```

`serviceAreaId` 从默认地址的 `serviceAreaId` 取。**如果地址没有 `serviceAreaId`（null），不要传该参数**，否则后端可能匹配不到。

**幂等键（关键）**：

```ts
// 进入页面时生成一次，整个页面生命周期内不变
private idemKey: string = util.generateRandomUUID(true);

// 提交
const created: BookingCreated = await ApiClient.post<BookingCreated>(
  '/customer/bookings',
  {
    serviceItemNo: this.param.itemNo,
    appointmentDate: this.selectedDate,
    serviceWindowCode: this.selectedWindow,
    addressNo: this.address!.addressNo,
    quantity: this.quantity,
    options: this.param.selectedOptions
  },
  { 'Idempotency-Key': this.idemKey }
);
```

> 后端三段式幂等：**同键 + 同内容** → 返回首次结果（安全重试）；**同键 + 不同内容** → `409 IDEMPOTENCY_CONFLICT`。所以：
> 1. 幂等键在页面初始化时生成，不要每次点击重新生成（否则失去防重意义）；
> 2. 提交成功跳转后，如果用户返回再改内容重提，必须**重新生成** key；
> 3. 按钮点击后立刻 `disabled`，双保险。

**`preview` 与 `create` 的区别**：
- `POST /customer/bookings/preview` 只算钱不落库，用于页面上的费用明细；
- `POST /customer/bookings` 才真正建单。
- 设计稿的费用明细用 `price-preview`（`/public/...`）就够，`preview` 可以省略一次请求。**二选一即可**，不要两个都调。

## 11. 关键业务流

### 11.1 登录

```
WelcomePage
  └─ Storage.getToken()
       ├─ 有 token ──→ MainPage ──→ HomeTab.onPageShow()
       │                              └─ GET /public/service-categories
       │                                    └─ 401? → clear token → LOGIN
       └─ 无 token ──→ LoginPage
                        └─ POST /auth/login
                             ├─ OK → Storage.setToken + setAccount
                             │        → pageStack.clear()
                             │        → push(MAIN)
                             └─ 失败 → 按错误码提示
```

### 11.2 预约下单

```
ServiceDetailPage
  └─ 收集 selectedOptions
       └─ push(BOOKING, { itemNo, selectedOptions })
            ├─ GET /customer/addresses          → 默认地址
            ├─ GET /public/availability         → 14 天时段
            │     (serviceItemNo, serviceAreaId?, dateFrom, dateTo)
            ├─ 改数量/加项 → POST /public/service-items/{itemNo}/price-preview
            │                (quantity, selectedOptions)
            └─ 提交
                 ├─ 生成/复用 Idempotency-Key（页面级，UUID）
                 ├─ 按钮 disabled
                 ├─ POST /customer/bookings
                 │    Header: Idempotency-Key
                 │    Body: { serviceItemNo, appointmentDate,
                 │            serviceWindowCode, addressNo, quantity, options }
                 ├─ OK → replacePath(PAYMENT, { orderNo, payableAmount, deadline })
                 └─ 409 SLOT_NOT_AVAILABLE → 重新拉时段 + 提示
```

### 11.3 支付

```
PaymentPage
  ├─ 倒计时基于 param.deadline（paymentDeadline）
  ├─ 点击"确认支付"
  │    ├─ channel 固定传 'MOCK'   ← 后端首版只有 MockPaymentGateway
  │    ├─ Idempotency-Key
  │    └─ POST /customer/bookings/{orderNo}/pay
  │         ├─ OK (PaymentCreated) → 成功态 → 2s → replacePath(ORDER_DETAIL)
  │         ├─ PAYMENT_ORDER_NOT_PAYABLE → 刷新订单，已支付则跳详情
  │         └─ PAYMENT_TIMEOUT → 提示重新下单
  └─ 倒计时归零 → 禁用按钮
```

### 11.4 评价

```
OrderDetailPage (status = COMPLETED 且 reviewStatus 为空)
  └─ push(REVIEW, { orderNo, serviceName })
       ├─ 4 维度星级（硬编码 REVIEW_DIMENSIONS）
       ├─ 总分 = 4 维度平均
       └─ POST /customer/bookings/{orderNo}/reviews
            Body: { dimensionScores: {SERVICE:5, ATTITUDE:5, QUALITY:5, PUNCTUALITY:5},
                    content: string, fileIds: [] }
            ├─ OK → pop() + 父页刷新
            └─ REVIEW_ALREADY_EXISTS → 提示 + pop()
```

### 12.2 明文 HTTP（必配，否则请求直接失败）

HarmonyOS 默认禁止 cleartext HTTP。后端是 `http://`，必须显式放行。

在 `entry/src/main/resources/base/profile/network_config.json`：

```json
{
  "network-security-config": {
    "base-config": {
      "cleartextTrafficPermitted": true
    }
  }
}
```

`module.json5` 的 `module` 节点加：

```json5
"metadata": [
  {
    "name": "ohos.net.http.NetworkSecurityConfig",
    "resource": "$profile:network_config"
  }
]
```

> **这是最容易漏的一步**。漏了会报 `2300006` 或请求直接 reject，而且错误信息看不出是明文 HTTP 的问题，会浪费半天。

### 12.3 模拟器与真机的地址差异

| 环境 | BASE_URL |
| --- | --- |
| DevEco 模拟器 | `http://10.0.2.2:8080/api/v1` |
| 真机（同一 WiFi） | `http://<电脑局域网IP>:8080/api/v1` |
| 真机（USB 调试） | 用 `hdc rport tcp:8080 tcp:8080` 后仍用 `127.0.0.1` |

真机调试时后端要监听 `0.0.0.0`（Spring Boot 默认就是），并检查 Windows 防火墙放行 8080。

这些是设计稿/设想与后端现状的**真实错位**，逐条给了应对方案。不处理会在开发中途卡住。

| # | 缺口 | 影响 | 应对 |

| 1 | 支付渠道首版只有 `MOCK` | 传 `WECHAT` 会 400 `PAYMENT_CHANNEL_DISABLED` | UI 展示三种，提交固定传 `MOCK`（见 9.10） |

## 14. 异常与边界矩阵

| 场景 | 表现 | 处理 |
| --- | --- | --- |
| 后端未启动 | 所有读接口超时 | Mock 兜底 + "演示数据"角标；写操作明确报错 |
| token 过期 | 任意接口 401 | 清 token → `clear()` → `LOGIN` |
| 弱网（8s 超时） | 请求 pending | 骨架屏 + 重试按钮 |
| 分类下无服务 | 列表空 | 空态插图 + "看看其他分类" |
| 无订单 / 无消息 / 无地址 | 列表空 | 各自空态文案 + 引导按钮 |
| 时段全部不可约 | 时段网格全灰 | "近期已约满，请选择其他日期" |
| 重复点击提交 | 幂等键相同 | 按钮 `disabled` + 后端幂等双保险 |
| 订单已支付又进支付页 | `PAYMENT_ORDER_NOT_PAYABLE` | 刷新状态 → 跳订单详情 |
| 已评价订单再进评价页 | `REVIEW_ALREADY_EXISTS` | 提示 + 返回 |
| 地址被其他端修改 | `ADDRESS_VERSION_CONFLICT` | 提示刷新 + 重新拉列表 |
| 图片加载失败 | `Image` 空白 | 用渐变块 + Path 占位（本方案无网络图，天然规避） |

**加载态统一**：首屏用骨架屏（灰块），局部刷新用 `LoadingProgress`。不要用全屏转圈，视觉上很廉价。

## 16. 答辩演示脚本

按这个顺序走，5 分钟能讲完所有亮点：

1. **冷启动** → 欢迎页（讲品牌色与 slogan 的设计意图）
2. **登录** → 输错密码看错误提示（讲错误码映射）→ 正确登录
3. **首页** → 分类宫格来自 `GET /public/service-categories`（不是写死的）
4. **列表** → 切分类、切排序（讲后端无排序参数所以前端排）
5. **详情** → 选规格 → 价格变化来自 `price-preview`（**金额全程服务端算，客户端改不了**，这是安全设计）
6. **预约** → 选日期看时段可用性（真实排班数据）→ 提交（讲 `Idempotency-Key` 防重复下单）
7. **支付** → 倒计时（讲 `paymentDeadline` 来自后端）→ 支付成功
8. **订单详情** → 6 段进度时间线（数据来自 `fulfillment` 接口，不是假动画）
9. **评价** → 4 维度打分 → 总分自动算
10. **我的** → 退出登录
11. **断网演示** → 关掉后端，回首页看 Mock 兜底 + "演示数据"角标（这一手很加分）

**可能被追问的问题，提前准备：**

| 问题 | 答案要点 |
| --- | --- |
| 为什么用 Navigation 不用 router | router 在 API 12 废弃；Navigation 支持类型安全参数和栈清空（登录后不能退回登录页） |
| 支付渠道为什么只传 MOCK | 后端首版只注册 `MockPaymentGateway`，`PaymentApplicationService` 校验 `gateway.channel().equals(channel)`，传其他值直接 400 |
| 幂等键为什么不是每次点击都生成 | 幂等的前提是"同一次业务意图用同一个键"。每次点都新生成，等于没有幂等 |
| 订单"待服务"为什么发两个请求 | 后端 `status` 只接受单个枚举值，`CONFIRMED` 和 `EN_ROUTE` 都属于待服务 |
| 为什么不用第三方 UI 库 | 鸿蒙三方库在 API 12 生态不稳定，且手写能精确还原设计稿 |
| 金额会不会被客户端篡改 | 不会，`price-preview` 和建单都不接收金额字段，全部服务端按快照算 |
| 401 怎么统一处理 | `ApiClient` 里拦截 `responseCode === 401`，清 token 后抛 `AUTH_TOKEN_EXPIRED`，由页面统一跳登录 |

## 附录 A：`router` 降级写法

如果教材强制 `router`：

```ts
// 跳转
router.pushUrl({ url: 'pages/ServiceDetailPage', params: { itemNo: 'SVC001' } });

// 取参
const params = router.getParams() as Record<string, string>;
const itemNo: string = params['itemNo'];

// 登录后清栈（router 没有 clear，只能 replace）
router.replaceUrl({ url: 'pages/MainPage' });
```

差别：`router` 无法真正清空历史栈，登录后按返回键可能回到登录页。规避方式是在 `LoginPage.onBackPress` 里 `return true` 拦截。这也是选 `Navigation` 的实际原因之一。

## 附录 B：ArkTS 严格模式约束清单

开发时最容易踩的 8 条：

| 约束 | 错误写法 | 正确写法 |
| --- | --- | --- |
| 禁止 `any`/`unknown` | `let data: any = res` | `let data: ApiResult<Category[]> = ...` |
| 对象字面量必须有类型 | `const o = { a: 1 }` | `const o: MyType = { a: 1 }` |
| `JSON.parse` 需转型 | `JSON.parse(s).code` | `(JSON.parse(s) as ApiResult<T>).code` |
| 禁止索引签名访问 | `obj[key]` | 用 `Map<string, T>` 或显式字段 |
| 禁止结构化类型 | 传"长得像"的对象 | 必须显式 `implements` 或同类型 |
| 不支持 `Object.assign` 合并 | `Object.assign(a, b)` | 逐字段赋值或写 `copy()` 方法 |
| 装饰器只用于 struct/class | 装饰普通函数 | 状态放 `struct` 里 |
| 函数重载受限 | 同名多签名 | 用可选参数或联合类型 |

另外：

- `ForEach` 的第三个参数（keyGenerator）**必须给**，否则列表更新会复用错节点；
- `@Prop` 是单向拷贝，`@Link` 才是双向；改父组件状态用 `@Link`；
- `Map` 的变化**不会**触发 `@State` 刷新，要改完重新赋值一个新 `Map`。

### D.4 代码里已规避的三个坑

1. **`Path` 坐标不缩放**：`NavIcon` 用 `Shape` + `viewPort({width:24,height:24})` 缩放，
   不能直接给 `Path` 设 `width/height`，否则 24 坐标系配 22 尺寸会裁掉图形。
2. **`JSON.stringify(Map)` 输出 `{}`**：评价维度用固定字段的 `DimensionScores`，
   不是 `Map` 也不是 `Record`（ArkTS 禁止动态索引赋值）。
3. **`http://` 被当成注释**：写静态检查脚本时，必须先抹掉字符串再抹注释，否则括号配对全乱。
