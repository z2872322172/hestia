# 家政服务预约垂直领域调研

## 1. 文档目的

本文回答以下问题：

- 家政服务预约到底是什么业务，与普通商品商城、泛本地生活平台有什么区别。
- 用户从找服务到完成履约的真实链路是什么。
- 行业目前最突出的痛点是什么，系统应优先解决哪些问题。
- 天鹅到家、好慷在家等代表性平台采用了什么服务模式。
- 一个本科毕业设计应该如何收敛范围，既不空泛，也不至于做成无法完成的大型商业平台。

本文面向需求分析、开题、系统设计和论文背景章节。具体功能清单与领域模型见 [02-产品需求与领域模型.md](./02-产品需求与领域模型.md)。

## 2. 领域定义

根据《国务院办公厅关于促进家政服务业提质扩容的意见》，家政服务业是：

> 以家庭为服务对象，由专业人员进入家庭成员住所提供或以固定场所集中提供对孕产妇、婴幼儿、老人、病人、残疾人等的照护以及保洁、烹饪等有偿服务，满足家庭生活照料需求的服务行业。[S1]

因此，家政平台的基本特征不是“销售商品”，而是：

- 服务对象是家庭。
- 服务发生在上门或家庭相关场景。
- 服务质量依赖服务人员的技能、健康、信用和现场执行。
- 交易完成后还有较长的履约、确认、评价和售后过程。
- 地址、电话、门牌、家庭成员情况等具有较强隐私属性。

本项目可以理解为“垂直家政领域的本地生活 O2O”，但业务范围必须收窄到家政服务，不应扩展为餐饮、酒店、团购等综合平台。

## 3. 市场与行业趋势

### 3.1 规模和需求基础

《中国家政服务业发展报告（2025）》给出的口径为：2024 年全国家政服务行业产值超过 1.2 万亿元，从业人数超过 3000 万人，相关企业和个体工商户接近 300 万家。[S2]

2026 年商务部专题发布会继续将家政服务业定位为万亿级民生产业，并提出标准化、职业化、产业化、信用平台和员工制转型等方向。[S3]

这些数据说明家政需求具有长期性，但在毕设中不应直接宣称“平台可以覆盖全国”。更合理的系统定位是：

- 面向单一城市或若干城区的预约平台。
- 支持若干家政公司、门店或自营服务团队。
- 先解决标准化上门服务的预约和履约。

### 3.2 消费行为变化

重庆、四川、陕西等七地消委会 2025 年联合调查显示：[S4]

| 指标 | 调研结果 | 对系统的启示 |
| --- | --- | --- |
| 家政服务消费普及率 | 81.69% | 家政不是极小众需求，用户端需要有清晰的分类和搜索 |
| 26 至 40 岁核心消费人群 | 50.79% | 移动端和网页端应强调效率、透明价格和快速预约 |
| 偏好小时工等灵活服务 | 38.57% | 按次、按时长预约是首版最重要的产品形态 |
| 超过半数年度预算集中在 1000 至 4999 元 | 需求属于中频消费 | 优惠券不是核心，复购、常用地址和历史订单更重要 |
| 每月或每季度定期使用为主 | 消费从应急型转向计划型 | 需要支持周期性预约、再次预约和固定服务人员 |
| 支持“增强规范化、明确行业标准” | 50.61% | 服务项目、价格、服务范围和服务标准必须结构化 |
| 支持“利用信息化维护行业准入门槛” | 40.84% | 人员资质、健康信息、审核状态应进入系统模型 |

### 3.3 行业主要矛盾

政策层面已经明确家政行业存在有效供给不足、发展不规范和群众满意度不高等问题。[S1] 具体到软件系统，可以归纳为以下矛盾：

- 用户需要透明和确定性，平台提供的价格、人员、时间和服务内容却经常不透明。
- 用户需要合适的人，平台缺少可信的技能、健康、信用和服务记录。
- 用户需要准时上门，平台缺少可靠的排班、时段占用和改派机制。
- 服务发生在家中，平台需要记录履约，同时必须保护隐私。
- 长周期服务和单次服务的交易、履约、结算方式不同，不能共用一套简单订单逻辑。

## 4. 家政服务的主要分类

### 4.1 按服务期限和交易方式分类

| 类型 | 典型服务 | 主要流程 | 系统难点 |
| --- | --- | --- | --- |
| 单次标准服务 | 日常保洁、深度保洁、擦玻璃、空调清洗 | 选服务、选时段、下单、派单、上门、完成、评价 | 时段库存、价格规则、人员匹配 |
| 周期服务 | 每周保洁、每月家电清洗 | 选择周期、固定人员、按次履约 | 周期排班、请假替换、按次结算 |
| 长期住家或白班服务 | 住家保姆、育儿嫂、老人照护 | 提交需求、顾问匹配、面试、签约、长期服务 | 合同、人员更换、工资结算、风险事件 |
| 咨询撮合服务 | 月嫂、高端管家、定制照护 | 留资、顾问联系、人工匹配、线下签约 | 线索跟进、人工流程、非标准化定价 |

这四类服务的产品逻辑不同。一个毕业设计如果全部做深，很容易形成“每块都有页面，但每块都无法闭环”的结果。

### 4.2 按业务品类分类

| 一级分类 | 二级示例 |
| --- | --- |
| 居家保洁 | 日常保洁、深度保洁、开荒保洁、退租保洁、玻璃清洁 |
| 家电清洗 | 空调、洗衣机、油烟机、冰箱、热水器 |
| 家务烹饪 | 做饭钟点工、备菜、餐后整理 |
| 母婴护理 | 月嫂、育儿嫂、0 至 3 岁婴幼儿居家照护 |
| 老人照护 | 居家陪护、助浴、陪诊、短时照护 |
| 整理收纳 | 全屋收纳、衣橱收纳、厨房收纳 |
| 家庭专项 | 除螨、除甲醛、养宠家庭保洁等 |

母婴护理和 0 至 3 岁婴幼儿照护已有专门国家标准，标准覆盖机构、人员、服务流程、质量评价与改进等内容。[S5] 这意味着母婴类服务不能只做一个普通商品 SKU，还需要资质、等级、服务流程和风险控制。

### 4.3 按用工和服务供给模式分类

| 模式 | 特点 | 优势 | 系统要求 |
| --- | --- | --- | --- |
| 员工制自营 | 平台或公司直接管理服务人员 | 质量、培训、调度更可控 | 人员档案、排班、考勤、工资或结算 |
| 商家入驻 | 家政公司入驻，平台聚合供给 | 供给扩张快 | 商家审核、服务审核、商家隔离、结算 |
| 个人撮合 | 独立服务人员接单 | 灵活、供给多 | 实名、资质、信用、纠纷处理难度高 |
| 混合模式 | 自营加商家或个体 | 兼顾质量与规模 | 角色和权限复杂，首版不建议全部实现 |

## 5. 核心角色与价值关系

| 角色 | 核心目标 | 系统职责 |
| --- | --- | --- |
| 消费者或雇主 | 快速找到可信服务并按时完成 | 搜索、预约、支付、查看进度、取消改期、评价投诉 |
| 家政服务人员 | 获得合适订单并完成履约 | 维护技能与档期、接单、上门签到、上传服务记录、查看收入 |
| 家政公司或商家 | 管理服务供给和人员 | 管理服务项目、人员、排班、订单、售后和结算 |
| 平台运营人员 | 审核供给、调度订单、处理争议 | 商家和人员审核、派单改派、订单监控、投诉处理、数据统计 |
| 平台财务或客服 | 处理资金和售后 | 支付记录、退款、结算、工单和审计 |

毕设首版不必把财务和客服拆成独立后台角色，可以由管理员兼任，但在权限和数据模型上要预留。

## 6. 用户从找服务到完成履约的完整旅程

### 6.1 标准单次服务

```mermaid
flowchart LR
    A[进入平台] --> B[选择城市和服务分类]
    B --> C[浏览服务项目]
    C --> D[填写地址并判断服务范围]
    D --> E[选择服务规格和增值项]
    E --> F[查看可用日期和时段]
    F --> G[确认价格和取消规则]
    G --> H[提交订单并支付定金或全款]
    H --> I[平台派单或商家接单]
    I --> J[服务人员接单]
    J --> K[上门签到]
    K --> L[执行服务并上传记录]
    L --> M[用户确认完成]
    M --> N[评价、投诉或再次预约]
```

### 6.2 周期服务

周期服务比单次服务多出：

- 周期规则，例如每周六上午。
- 固定服务人员和备用人员。
- 单次履约记录与整份周期合同分离。
- 服务人员请假后的替换。
- 按次结算、暂停、恢复和终止。

### 6.3 长期住家服务

长期住家服务更接近“人员匹配 + 合同 + 持续服务”，不是按时间段购买一个保洁 SKU。其重点是：

- 需求画像和人工顾问。
- 人员面试、背景和健康核验。
- 三方合同。
- 服务期内的调换和风险事件。
- 工资、服务费和保险。

## 7. 行业痛点与产品机会

| 用户痛点 | 典型表现 | 系统可提供的解决能力 |
| --- | --- | --- |
| 价格不透明 | 基础价、时长、面积、耗材、加项和上门费不清楚 | 结构化计价规则、订单价格快照、支付前明细确认 |
| 人员资质不透明 | 看不到健康、证书、经验和平台审核状态 | 人员档案、证书有效期、审核记录、前台可信展示 |
| 时间不确定 | 下单后才知道有没有人，临时取消或迟到 | 可用时段、时段锁定、接单超时、自动改派、迟到记录 |
| 服务质量不稳定 | 同一服务不同人员结果差异大 | 服务标准、检查项、过程照片、完成确认和评价 |
| 售后困难 | 出问题后责任不清，缺少证据 | 服务记录、异常上报、投诉工单、退款和改派流程 |
| 隐私和安全风险 | 家庭地址、门禁、儿童和老人信息暴露 | 最小化收集、字段脱敏、授权访问、操作审计 |
| 重复预约操作繁琐 | 周期用户每次都要重新填写 | 常用地址、历史服务单、再次预约、周期计划 |
| 供给不匹配 | 区域、技能、时间和用户需求不匹配 | 服务区域、技能标签、人员档期和派单规则 |

七地消委会调查明确指出，服务资质不透明、价格不透明、过度营销和售后维权难是突出问题，并建议线上平台加强入驻审核、价格监控、售后保障和纠纷解决。[S4]

## 8. 代表性平台调研

### 8.1 天鹅到家

公开官网展示的业务特征：[S6]

- 覆盖保姆、月嫂、保洁等综合家庭服务。
- 按家庭照护、母婴护理、居家清洁三类需求组织服务。
- 用户可以提交服务需求，顾问通常在 1 小时内联系，签约后根据档期安排上门。
- 上户前包括身份核验、背景信息核查、健康体检和服务规范考试。
- 订单配置保障方案，服务人员不适配时支持协调更换。
- 官网同时承担服务展示、城市选择、预约留资和知识内容功能。

可借鉴点：

- 服务分类围绕家庭需求，而不是围绕商品类别。
- 信任机制要贯穿下单前、服务中和售后。
- 月嫂等复杂服务可以采用“在线预约 + 人工确认”，不必强行全部自动化。

### 8.2 好慷在家

公开官网展示的业务特征：[S7]

- 采用员工制服务人员，由企业统一招聘和管理。
- 居家保洁强调标准化流程，单次标准服务 4 小时，按区域和顺序执行。
- 服务过程可视化，并提供一定时限内的不满意重做机制。
- 人员上岗前需要培训、实操、理论和身份、健康、技能认证。
- 主要服务包括居家保洁、收纳整理、专区清洁、做饭保姆、电器蒸洗、星级月嫂等。

可借鉴点：

- 标准化服务不应只写一句简介，而应有服务范围、时长、检查项和完成标准。
- 自营模式对排班、人员管理和履约记录要求更高，但数据模型更清晰。
- “完成”不应只由订单状态决定，还应有服务记录和用户确认。

### 8.3 京东家政、58 到家、美团等综合入口

综合平台通常采用以下模式：

- 通过标准商品化 SKU 展示服务、价格和可选时间。
- 用户下单后由平台或商家分配服务人员。
- 部分服务允许指定人员，部分服务由系统随机分配。
- 评价、售后和平台客服承担较强的售后兜底。

对本项目的启示：

- 单次保洁适合商品化 SKU 和固定计价规则。
- 需要把“商家”和“服务人员”分开。商家是供给组织，服务人员才是实际履约者。
- 如果系统只能管理商家，不能管理具体服务人员、技能和档期，就不能算完整的家政预约平台。

### 8.4 竞品模式总结

| 维度 | 综合平台型 | 员工制自营型 | 本项目建议 |
| --- | --- | --- | --- |
| 供给方式 | 商家或个体入驻 | 公司统一管理 | 商家入驻加服务人员管理 |
| 服务标准化 | 中等，依赖商家 | 高，有固定 SOP | 首版做结构化服务标准 |
| 排班能力 | 必要 | 核心能力 | 作为主要技术增量 |
| 信任机制 | 审核、评价、保障 | 自培、自检、保障 | 资质、档期、履约记录和投诉 |
| 实现复杂度 | 高 | 中高 | 收敛为标准预约型服务 |

## 9. 后端必须理解的业务规则

以下规则是系统设计建议，不是行业强制法律规则。默认值应做成配置项。

### 9.1 服务范围

- 服务项目必须绑定可服务区域，不能只按城市判断。
- 地址超出范围时，应在提交订单前拦截。
- 商家、服务人员和服务项目可以分别设置服务区域，最终取交集。
- 跨区可能产生上门费，应作为订单明细而不是临时改价。

### 9.2 价格计算

- 基础价、时长、面积、数量、加项和上门费应分别结构化。
- 订单必须保存价格快照，后续服务项目改价不能影响历史订单。
- 优惠券、平台补贴和实付金额应分开记录。
- 现场增加服务必须先追加明细并得到用户确认，不允许只修改总价。

### 9.3 时段和排班

- 可预约性取决于服务人员档期、服务时长、路上缓冲和服务区域。
- 一个服务人员同一时间段只能承接一个有效订单。
- 下单和锁定时段必须在同一事务中完成。
- 超时未支付应释放时段。
- 改期应先锁定新时段，再释放旧时段，避免丢失新时段。
- 服务人员请假或被停用后，应能触发改派而不是直接取消订单。

### 9.4 派单和接单

- 派单记录与订单状态应分离，一个订单可以经历多次派单和改派。
- 服务人员接单前，用户看到的应是“待接单”而不是“已确认”。
- 接单需要有超时机制，超时后重新进入派单池。
- 改派要保留原人员、原因、操作人和时间。
- 人工派单和抢单可以共用订单分配模型。

### 9.5 订单状态

建议的 MVP 状态：

```text
待支付
  -> 待派单
  -> 待接单
  -> 已接单
  -> 服务中
  -> 待用户确认
  -> 已完成
```

异常分支包括：

- 待支付/待派单/待接单可取消。
- 已接单后取消可能需要商家确认或扣除上门费。
- 服务中可发起异常或售后。
- 已支付订单退款应生成独立退款记录，不能只把支付状态改回未支付。
- 评价和投诉不要直接作为订单主状态，应使用独立的 `review_status` 和 `after_sale_status`。
- 已完成订单仍可以评价、投诉或申请售后，订单主状态保持不变。

### 9.6 完成与验收

- 服务人员点击完成不等于平台最终完成。
- 可以要求上传服务前后照片、检查项结果和用户签字或验证码。
- 用户确认后进入已完成。
- 可配置超时自动确认，但必须提前告知用户。
- 完成后一段时间内允许申请售后。

### 9.7 取消、改期和退款

- 取消规则应在下单前展示，并在订单中保存规则快照。
- 改期不是取消后重新下单，否则会丢失历史关系和优惠信息。
- 退款金额需要区分服务费、上门费、耗材费和优惠券。
- 已使用的优惠券是否退回应按规则处理。

### 9.8 评价、投诉和信用

- 评价维度至少包括服务质量、态度、准时和专业度。
- 投诉应允许关联订单、服务记录、图片和聊天或沟通记录。
- 投诉状态和订单状态应分开。
- 只有经过处理的投诉才能影响人员信用分。
- 评价和投诉都需要防篡改和操作审计。

## 10. 合规与数据保护

家政平台会处理姓名、电话、地址、门牌、家庭情况、证件、健康证明等信息。根据《个人信息保护法》：[S8]

- 处理个人信息应遵循合法、正当、必要和诚信原则。
- 收集范围应限于实现目的的最小范围，不得过度收集。
- 应公开处理规则，明示目的、方式和范围。
- 医疗健康、特定身份、行踪轨迹等属于敏感个人信息。
- 处理敏感个人信息应有特定目的和充分必要性，并取得单独同意。
- 应告知敏感信息处理的必要性和对个人权益的影响。

落实到系统设计：

- 用户端和服务端展示地址、电话时按角色和业务阶段脱敏。
- 身份证、健康证明等文件使用受控访问地址，不直接暴露在公开 URL。
- 服务人员只能查看已接订单所需的用户信息。
- 订单完成后按规则限制历史地址和电话的访问。
- 管理后台查询敏感字段和导出数据必须记录审计日志。
- 支付和地图等第三方密钥不得硬编码在公开仓库。
- 服务人员健康与证件信息不应在普通商品详情页公开。

## 11. 毕设范围收敛建议

### 11.1 推荐的首版定位

> 面向单一城市或若干城区的标准化上门家政服务预约平台，支持消费者选择服务与可用时段，家政公司或平台完成人员匹配，服务人员完成接单和上门履约，用户确认并评价。

首版角色：

- 消费者。
- 家政服务人员。
- 家政公司管理员或平台运营人员。

如果系统是自营模式，可以将家政公司管理员合并到平台管理员，但数据模型中保留服务组织。

### 11.2 推荐首版服务类型

- 日常保洁。
- 深度保洁。
- 开荒保洁。
- 玻璃或家电清洗。
- 整理收纳。

这些服务具有相对明确的价格、时长和验收方式，适合实现完整的时段预约和履约闭环。

### 11.3 建议暂不作为 MVP 主链路

- 住家保姆长期合同。
- 月嫂和育儿嫂的复杂人工撮合。
- 真实支付清算。
- 实时地图轨迹。
- 保险理赔。
- 服务人员工资发放。
- 多城市加盟商结算。
- 复杂推荐算法。

这些能力可以作为后续扩展或论文中的展望，不应阻塞首版闭环。

### 11.4 适合形成技术增量的部分

| 方向 | 可写进论文的技术点 |
| --- | --- |
| 时段预约 | 时段库存、并发锁定、超时释放、改期一致性 |
| 人员匹配 | 服务区域、技能、评分、档期和订单金额的多条件匹配 |
| 履约记录 | 签到、服务项勾选、照片证据、用户确认 |
| 订单状态机 | 状态合法性校验、操作留痕、异常分支处理 |
| 售后 | 投诉工单、退款关联、处理时效和人员信用 |
| 权限与隐私 | 多角色数据隔离、敏感字段脱敏、审计日志 |

## 12. 调研结论

1. 家政服务预约平台的核心是服务履约，不是商品交易。
2. 单次标准服务最适合作为毕业设计首版，周期服务和长期服务应明确放到后续范围。
3. 商家、服务人员、服务项目、人员技能、可用时段和上门订单必须分开建模。
4. 平台可信度取决于人员资质、价格透明、时段确定性、履约记录和售后机制。
5. 技术上最值得投入的是时段预约一致性、订单状态机、权限隔离和履约证据。
6. 论文中应写清平台边界，避免把“家政服务平台”泛化成综合本地生活电商。
