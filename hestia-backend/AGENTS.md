# Hestia 后端开发约束

本文件适用于 `hestia-backend` 下的所有代码、配置、SQL、测试和文档修改。

## 1. 约束优先级

发生冲突时，按以下顺序执行：

1. 用户当前明确提出的要求。
2. 本文件中的项目约束。
3. `docs/modules/` 中最新的业务模块详细设计。
4. `docs/06-第一阶段最小骨架集成.md` 中的当前阶段要求。
5. 其他历史设计文档。

早期文档中的多商家入驻、个人开店、平台抽佣和开放抢单内容均不是当前实施范围。

## 2. 项目基本边界

- 使用 Java 17、Spring Boot 3.5.x、Maven 单工程。
- 包名保持 `com.housekeeping.platform`。
- 采用模块化单体，不拆微服务，不增加 Maven 子模块。
- 按业务模块垂直分包，禁止建立全局平铺的 `controller`、`service`、`mapper` 目录。
- 当前业务模式为单公司自营，不做商家入驻、商家分账和平台抽佣。
- 服务人员分为全职和兼职，不引入 `provider_id` 或商家归属。
- 首版不做开放抢单池，采用系统派单、人员确认和运营改派。
- MySQL 是订单、支付、排班和履约等核心业务状态的唯一事实来源。
- Redis、RocketMQ、MinIO 和地图服务都是基础设施，不能替代数据库事务。
- 所有表结构必须通过 Flyway 管理，禁止使用 `ddl-auto` 或 MyBatis-Plus 自动建表。

## 3. 代码规范

所有 Java 代码必须遵守《阿里巴巴 Java 开发手册》现行版本。

至少满足以下要求：

- 类、方法、变量、常量、包和接口命名必须语义清晰，不得使用无意义缩写。
- 常量不得散落为魔法值，状态码、错误码、配置键必须有统一常量或枚举。
- 金额使用 `BigDecimal`，禁止使用 `double` 或 `float` 参与金额计算。
- 时间使用 `LocalDate`、`LocalTime`、`LocalDateTime`，禁止混用旧版日期 API。
- 集合初始化应预估容量，禁止在循环中创建不必要对象。
- 禁止使用 `System.out`、`System.err` 输出日志。
- 日志使用 SLF4J 参数化写法，禁止字符串拼接日志。
- 禁止捕获异常后不处理、不记录或直接吞掉。
- 禁止捕获 `Throwable`，业务异常使用项目统一异常体系。
- 对外接口不得直接返回数据库实体，必须转换为 DTO 或 VO。
- 所有外部输入必须校验，不能信任前端传入的身份、金额、状态和权限字段。
- 集合、字符串和对象比较必须避免空指针，优先使用成熟工具方法或显式判空。
- 线程池必须由 Spring 管理或显式定义，禁止随意使用无界队列和默认线程池。
- 禁止在事务方法中进行长时间外部调用。
- `@Transactional` 只放在应用服务层，并明确回滚条件，禁止在 Controller 或 Mapper 中声明事务。
- 禁止通过同类内部方法自调用绕过 Spring 事务代理。
- 代码格式应保持一致，默认 4 个空格缩进，单行不宜超过 120 个字符。
- 新增依赖必须说明用途，并检查与 Spring Boot 版本的兼容性。

## 4. 注释要求

注释必须解释“为什么”和“业务约束”，不能简单重复代码。

- 所有公开类、接口和枚举必须有类级注释，说明职责和业务边界。
- 所有公开方法必须有 Javadoc，说明用途、关键参数、返回值、异常和副作用。
- 状态机、计价规则、时段锁定、幂等、权限判断和并发控制必须写清楚不变量。
- 复杂 SQL、条件更新和事务边界必须注释说明原因。
- 对非常规业务规则，应标明依据或对应模块文档。
- 注释使用中文，代码标识符、日志关键字和数据库字段保持英文。
- 修改业务规则时，必须同步修改对应注释，禁止保留过期注释。
- 禁止无意义注释，例如“给变量赋值”“调用方法”。
- `TODO` 必须说明原因、后续处理和触发条件，不能留下无法理解的待办。

## 5. 模块边界

业务模块之间优先通过 Application Service、Port 接口或领域事件协作。

必须遵守：

- Controller 只负责协议适配、参数校验和调用应用服务。
- Application Service 负责用例编排、事务、幂等、权限和数据范围。
- Domain 负责状态机、计价、时段、派单和履约规则。
- Infrastructure 负责 MyBatis、Redis、文件、消息和外部服务适配。
- 禁止跨模块直接调用 Mapper。
- 禁止跨模块直接修改对方业务表。
- 禁止业务模块依赖 `admin` 或 `operations` 私有实现。
- 禁止把业务规则写进 Controller、Mapper XML 或定时任务类。
- 通用能力放入 `common`，但 `common` 不能依赖任何业务模块。
- 订单主状态只能由订单模块的应用服务修改。
- 支付、派单、履约、售后和评价分别维护自己的状态。

## 6. 改动联动要求

任何代码改动都不能只保证“当前文件能编译”，必须检查涉及的上下游模块。

修改以下内容时，必须搜索并更新所有使用方：

- 数据库表字段、索引、唯一约束和状态枚举。
- DTO、VO、请求参数、响应结构和错误码。
- 应用服务公开方法、Port 接口和领域事件。
- 订单、人员、时效、支付和履约状态机。
- 角色权限、数据范围和敏感字段展示规则。
- Flyway 迁移、样例数据、Swagger 文档和 README。

常见联动参考：

| 改动位置 | 必须检查 |
| --- | --- |
| 账号、角色、数据范围 | 客户、人员、运营、所有鉴权入口 |
| 服务项目、价格、服务标准 | 人员技能、排班、报价、订单、履约 |
| 服务区域 | 客户地址、账号区域权限、人员区域、派单、统计 |
| 排班和时段 | 订单创建、支付超时、取消、改期、派单 |
| 订单状态或字段 | 派单、支付、履约、售后、通知、运营查询 |
| 支付或退款 | 订单摘要、订单取消、售后、通知、报表 |
| 履约状态或证据 | 订单状态、售后、通知、运营监控 |
| 评价和售后 | 订单售后摘要、人员质量统计、派单评分 |
| 错误码或统一响应 | API 文档、前端契约、异常处理、测试 |

如果无法确认影响范围，先搜索、阅读相关模块文档和调用链，再进行修改。

## 7. 数据库约束

- 表名和字段名使用 `snake_case`。
- 表使用 InnoDB 和 `utf8mb4`。
- 主键使用 `BIGINT UNSIGNED` 自增，业务编号单独保存。
- 金额使用 `DECIMAL`，时间使用 `DATETIME(3)`。
- 状态字段使用稳定的英文枚举字符串。
- 账号、订单、支付、退款和审计日志不做物理删除。
- 地址使用状态软删除，订单必须保存快照。
- 关键唯一性必须使用数据库唯一索引兜底。
- 状态合法性应尽量使用 `CHECK` 约束和 Java 枚举共同保证。
- 乐观锁字段统一使用 `version`。
- 普通可变业务表必须包含 `created_at`、`created_by_account_id`、`updated_at`、`updated_by_account_id` 和 `version`。
- 创建人和修改人保存账号 ID，不保存姓名；系统操作允许为空并记录操作来源。
- 日志、支付回调、证据和状态历史等只追加表只保留创建时间或实际操作人，不强行增加修改人。
- 审计字段通过 MyBatis-Plus 的 `MetaObjectHandler` 或统一应用服务填充，禁止每个业务方法重复手写。
- `created_by` 和 `updated_by` 只表示最后一次操作，修改历史必须写状态日志或 `audit_log`。
- 高频查询必须建立与查询条件一致的联合索引。
- 禁止全表扫描后内存分页。
- 禁止字符串拼接 SQL，所有参数必须参数化。
- 已执行的 Flyway 文件不能修改，只能新增迁移。
- 跨模块业务表原则上使用逻辑外键和索引，避免级联删除和迁移循环依赖。

## 8. API 与异常规范

- API 统一使用 `/api/v1` 版本前缀。
- 公共、消费者、服务人员、运营和管理接口按角色分组。
- 所有接口返回统一响应结构，分页返回统一分页结构。
- 错误码必须稳定、可读，并与 HTTP 状态码配合。
- Controller 使用 Jakarta Validation 校验请求参数。
- 权限判断和数据范围判断必须在后端完成。
- 不得仅依赖前端隐藏按钮实现权限控制。
- 业务状态冲突返回 409 或项目约定的业务错误码。
- 未预期异常不得把堆栈和 SQL 返回给客户端。
- 重复提交、重复支付、重复回调、取消、改期和退款必须考虑幂等。

## 9. 安全与隐私

- 密码使用 BCrypt，禁止保存和输出明文密码。
- JWT 密钥、数据库密码、MinIO Secret 和地图 Key 必须来自环境变量。
- 禁止把任何真实密钥、账号或 Token 写入代码、配置、测试和文档。
- 完整手机号、门牌、证件号和履约照片不得写入普通日志。
- 私有文件必须经过权限校验或短期签名访问。
- 服务人员只能查看分配给自己的订单和履约信息。
- 运营人员只能访问授权服务区域的数据。
- 敏感操作必须写审计日志。
- 生产 profile 必须关闭 smoke API、固定验证码和模拟管理员入口。

## 10. 测试要求

- 修改或新增业务代码必须补充对应测试。
- 修复缺陷必须增加能复现问题的回归测试。
- 状态机、计价、权限、幂等和并发逻辑必须有单元测试。
- 涉及 SQL、Flyway、唯一索引和事务的功能应有集成测试。
- 同一人员同一时段并发下单只能有一个成功。
- 重复支付、重复回调、重复取消和重复退款必须测试幂等。
- 跨用户、跨人员和跨区域访问必须有拒绝测试。
- 不得为了通过测试而删除有效断言或降低测试覆盖范围。
- 提交前至少执行 `mvn clean verify`；无法执行时必须说明原因。

## 11. 修改流程

执行任何开发任务时按以下顺序进行：

1. 阅读本文件和对应模块文档。
2. 检查当前代码、数据库迁移和相关调用方。
3. 明确本次改动影响的模块和状态。
4. 先修改领域规则和数据库结构，再修改应用服务和接口。
5. 同步修改 DTO、VO、错误码、Swagger 和文档。
6. 补充或修改测试。
7. 运行格式检查、单元测试和集成测试。
8. 汇总修改内容、联动模块、验证命令和未解决风险。

## 12. 禁止事项

- 禁止在未理解业务状态机的情况下直接修改状态字段。
- 禁止为了快速通过而绕过权限、事务、幂等或唯一约束。
- 禁止把 Redis 当作订单、支付或排班的唯一数据源。
- 禁止用消息队列替代核心数据库事务。
- 禁止在 Controller、定时任务或 Mapper 中复制领域规则。
- 禁止跨模块直接操作 Mapper 或修改其他模块的表。
- 禁止返回数据库实体、暴露密码哈希和内部密钥。
- 禁止无说明地重构无关模块或改动用户已有修改。
- 禁止使用破坏性 SQL、清空数据库或删除已应用迁移。
- 禁止在没有测试的情况下宣称功能完成。
